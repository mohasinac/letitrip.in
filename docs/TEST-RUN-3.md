Full-catalogue regression run against **https://www.letitrip.in**, driven case by
case with a real browser. Unlike runs 1 and 2, **defects are fixed inside the
run** rather than collected for some later pass that never happens — and this
file is the durable record of what was tested, what failed, what was fixed, and
what still needs a human.

> 🛑 **Cadence changed at batch 22 (2026-09-29).** Testing and fixing are now
> separate phases: a batch **records**, and one fix phase clears the whole
> backlog every **25 batches**, together with the publish + deploy. The original
> rule was "no batch advances with an open defect" — stricter-sounding, and
> worse. An `appkit` fix is not live on production until the milestone publish,
> so a fix made during batch 3 could not be re-driven during batch 3; it was
> recorded `pending-deploy` and verified at batch 25 anyway. The per-batch gate
> bought nothing the milestone was not already buying, while turning each batch
> into two cases of testing plus a defect traced through four layers, an appkit
> rebuild and a full `npm run check`.

> **Accepted cost, stated plainly:** batches 2–25 run against code that does not
> carry batch 1's fixes, so a later batch can rediscover a defect an earlier one
> already found. Every row carries its batch number and every ledger entry its
> `pending-deploy` state, so the re-drive list at each milestone is computed
> rather than remembered.

## How to read this

Every number in the block above is **computed from the verdict files on disk** by
`scripts/test-run-status.mjs`. None of it is typed by hand — an earlier run's
hand-kept tally reported 17 failures where the files held 15, because the prose
had been counting calibration controls and nothing could catch it.

| Column | Meaning |
|---|---|
| **Batch** | Which batch produced the row. Production changes at each deploy milestone, so a pass recorded before one is not evidence about the build after it — this column is what makes that reconstructable |
| **#** | Running case count across the whole run |
| **Case id** | The checklist id. Also what a fix must name (G4) |
| **Test name** | The case's `label` — the claim it exists to settle |
| **Group/Page** | Where in the catalogue. A case id alone does not say |
| **Role** | guest / buyer / seller / admin. The same page behaves differently for each, and that difference is usually the bug |
| **Result** | ✅ pass · ❌ fail · ⬜ null. `null` is "could not test" and is first class — a fabricated pass is a false green nobody revisits |
| **Reason** | What was observed. Quoted screen text, an HTTP status, or a console error. Never "looked wrong" |
| **Screenshot** | Taken at the moment of judgement, for **every** verdict including passes. A pass with no image is unfalsifiable |
| **Fix applied** | What changed. Empty on a pass |
| **Files changed** | Makes the fix reviewable without hunting a commit |
| **Manual?** | The case needs a channel the browser has not got — a real inbox, an interactive Google account |
| **Re-verified** | Whether the fix was re-driven against production. A fix nobody re-tested is a hypothesis |

Results marked `retracted` are corrections of an earlier row in this table. They
are added as **new rows**, never silent edits — a previous run recorded that two
brand pages rendered empty, and direct navigation later showed 20 and 8 products.
That retraction is part of the record.

## Fix-and-deploy cadence

🛑 **Testing and fixing are separate phases.** A batch **records** — verdict,
evidence, screenshot, and the cause if one turn of looking finds it. Every 25
batches, one fix phase clears the whole backlog together with the publish and
deploy. `fixCycleEvery === deployEveryBatches === 25`, and **the two must stay
equal**: a fix phase without a deploy produces fixes nobody can verify.

**Why the earlier, stricter-sounding rule was worse.** It was "no batch advances
with an open defect". But an `appkit` fix is not live on production until the
milestone publish, so a fix made during batch 3 could not be re-driven during
batch 3 — it was recorded `pending-deploy` and verified at batch 25 anyway. The
per-batch gate bought nothing the milestone was not already buying, while making
every batch a mixed workload: two cases of testing, then a defect traced through
four layers, an appkit rebuild, and a full `npm run check`.

**The accepted cost.** Batches 2–25 run against code lacking batch 1's fixes, so
a later batch can rediscover a defect an earlier one already found. Each row
carries its batch number and each ledger entry its `reverified` state, so the
re-drive list at every milestone is **computed, not remembered**.

At each milestone, three sources are drained, not one: open defects from
`test-run-status.mjs`, the G5 overflows in `state.fixQueue` (each with a recorded
`nextStep`), and `TEST-RUN-3-OUTOFSCOPE.md` — decided per entry, because an
untouched list is one nobody reads by milestone three.
