## Can we launch? — the open blockers

Measured on production, not estimated. Carried from `LAUNCH-STATUS.md` at the
point that file was folded in; **renumbered**, because it had shipped with `6`
printed before `5`.

### 1. Every cart / checkout 400 is silent

Three observed, each with a clear user-safe server message and **0
`[role=alert]`, 0 `[role=status]`**, with the message absent from the DOM
entirely. The buyer clicks and the button appears dead.

**Fix:** pipe through `toUserMessage(code, t)` into a toast or inline error, per
Rule #9's server-error path. Never fall back to the raw server message
(Root Cause #86).

### 2. A seller cannot create a listing from the quick-add form 🛑

On `/store/products/new` the required product image **never registers**: the
upload shows progress reaching 50%, clears, and the field still reads *"Product
image is required"*, so Publish is refused forever.

**Decisive evidence:** across the whole session there was **not one** request to
`/api/media/sign`, `/api/media/finalize` or `storage.googleapis.com`. The
documented sign → PUT → finalize flow never runs. The percentage implies XHR
(`fetch` cannot report upload progress) and a `fetch` interceptor captured
nothing.

**The working reference is in the same codebase:** the payment-proof uploader on
`/user/orders/{id}/payment` performs the full chain correctly against the same
bucket.

🛑 **Scope, 2026-10-04 — the edit form fails too, one step later.** On
`/store/products/{slug}/edit` the upload half is **healthy** (sign 200 → PUT 200
→ finalize 201, three cycles, editor reads "3/10 images · 1/1 video") and then
**saving discards it** — `GET /api/products/…` reports `video` absent.

### 3. A seller cannot mark an order shipped 🛑

The Shipment panel on `/store/orders/{id}/view` accepts Carrier and Tracking
number; Save closes the drawer and navigates back as though it worked; after a
reload **both fields are empty and the status is unchanged**. No error anywhere.

Attempted twice on a real order, the second time reading the values back out of
the fields immediately before Save (`QA123456789` / `QA Carrier`, both present).
They reached the form and were not persisted. The write is a Server Action, so
nothing appears in a `fetch` interceptor and the navigation happens either way.

**Consequence: the money path stops at `paid`.** The buyer never receives
tracking and the order can never reach delivered.

### 4. A digital code bought with Cash on Delivery can never be collected 🛑

Driven end to end on production. `Buy Now` → address → **Cash on Delivery**
placed `order-1-20261004-diayd8` cleanly; `/user/digital-codes` then shows a
**Reveal Code** button which answers *"Could not retrieve your code. Please try
again."*

Retrying cannot work. The reveal route gates on order status —
`ALLOWED_STATUSES = {confirmed, processing, delivered}` — and a COD order starts
`pending`. For a physical good COD resolves on handover; **a digital code has no
handover**, so nothing advances the order and the gate never opens.

**The gate is right; offering COD here is not.** Releasing a redemption code
before payment gives the goods away. Withhold Cash on Delivery when an order
contains only digital-code items — manual UPI already works end to end, because
admin verification moves the order to `paid` / `processing`.

**Second, smaller defect in the same click:** the server returned the actionable
*"Code is only available after payment is confirmed"* and the UI replaced it with
*"please try again"*. Rule #9's server-error path again.

### 5. Minor — `Submit Proof` enables on the fraud checkbox alone

Clicking it with `buyerMarkedPaid` unticked fires nothing and writes nothing,
while the upload itself has already succeeded — so the page looks right and the
order keeps `paymentProofUrl: null`.

## Standing constraints — do not relax these

Carried from the batch-204 handoff. These are about the **harness**, and they
hold for every future run.

- **Never save Site Settings.** PRESERVE tier, one "Save all changes" over a
  37-group singleton with 21 live API keys behind it. Refused for an entire run.
  The baseline for whoever does it with a human present is
  `docs/TEST-RUN-3-SITESETTINGS-BASELINE.json`.
- **Never call** `/api/auth/login|session|me` — one 10-req/min IP bucket.
- **Never modify** a user account, login, saved address, or Site Settings.
- A claimed batch **restarts from case 1**. Never resume mid-batch.

### Two durable findings from that handoff

- **`/api/faqs` missing composite index** — **33 recorded occurrences** of
  `9 FAILED_PRECONDITION`, visible on `/admin/maintenance/server-errors`. The
  remedy is the one that worked for the seller sorts: reproduce the query against
  Firestore **with a control** (a query that should succeed — that is what pins
  the cause instead of guessing), read the required index out of the thrown error,
  add it to `appkit/firebase/base/firestore.indexes.json`, then
  `npm run firebase -- generate` → `deploy --only indexes` →
  `wait-for-indexes.mjs`, then re-drive. **A fix nobody re-tested is a
  hypothesis.**
- **React #418 is operational, not cosmetic, and still unowned.** 981 of 1,606
  `serverErrors` rows are `CLIENT_WINDOW_ERROR` hydration mismatches (**61%**).
  They crowd the recent window, so a `limit(12)` query returns only hydration
  noise and real 500s look unrecorded. **No case owns this. Write one.** Consider
  whether client errors belong in the same collection as server errors, or need
  separate retention.

## 🛑 Measurement traps — each of these produced a wrong answer first

- **Print the match context before filing a credential leak.** Twice a broad
  regex matched i18n **labels** (`"metaPageAccessToken":"Meta Page Access Token"`)
  rather than values. Both would have been false security findings.
- **Bash cwd persists between calls.** A `cd` into the appkit submodule silently
  broke a later root `git add`, and an `echo` printed success over the failure.
  Use absolute paths.
- **Include `\.` when scanning for float artifacts.** Without it
  `227453.66999999998` reads as two separate implausible integers.
- **A nonsense control is the only way to test a filter.** A real search term
  returns plausible rows whether or not filtering works — measured on `/stores`,
  where `?q=zzzznope` returned two real store cards and no empty state
  (Root Cause #99).
- **203 failures are not 203 defects.** On the core happy-path slice **6 of 7
  were already fixed and never re-driven**, and only 12% of failure comments carry
  prediction language. Re-verify before fixing (Rule #4).
- **669 nulls are mostly capability gaps, not untestable cases.** 48 were refused
  for needing a "human channel" that is mostly email, which
  `tester/scripts/check-inbox.mjs` can already read.
- **🛑 Re-drive a "this whole thing is broken" reading from a fresh navigation
  before recording it.** Six false defects were nearly filed in one session — the
  checkout address card, the admin Delete menu, seller order rows,
  `/admin/sections` controls, the admin Verify Payment button, and a wrong address
  state. Every one was a selector or procedure error, and every one was caught
  only by re-driving.
